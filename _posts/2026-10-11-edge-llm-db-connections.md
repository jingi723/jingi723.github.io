EDGE의 ETF 분석은 원천 자료를 읽고 LLM을 호출한 뒤, 분석 결과와 그 근거를 PostgreSQL에 저장한다. 전망 결과를 오전 8시까지 준비하려고 병렬 실행을 검토하던 중, 분석 한 건이 LLM 응답을 기다리는 동안에도 쓰기용 DB 연결 세 개를 유지한다는 제약이 드러났다.

SQL을 실행하지 않는 동안 연결을 반환하면 더 많은 분석을 실행할 여지가 생긴다. 하지만 당시 연결은 데이터 저장뿐 아니라 같은 분석이 겹치지 않도록 잡아 둔 세션 락도 유지했다. 연결을 닫는 변경에는 그 락이 맡던 역할을 어디로 옮길지에 대한 답이 필요했다.

내가 제기한 문제는 LLM 대기와 DB 연결의 수명을 분리할 수 있느냐는 것이었다. 별도 만료 시간을 가진 실행권을 바로 추가하기보다, 이미 사용하던 Step Functions 실행 ARN과 실행 슬롯을 재사용하는 방식을 먼저 검토하기로 했다. 조사·구현·실험은 AI 에이전트가 수행했고, 나는 적용 방향과 단계별 유료 실험, 실험 뒤 설정 복원을 결정했다.

## 분석 한 건이 LLM 대기 중에도 쓰기 연결 세 개를 유지했다 {#connection-lifetime}

기존 클라우드 워커의 연결 세 개는 각각 역할이 있었다. 하나는 ETF 단위 중복 실행과 동시 실행 수를 제한하는 락을 유지했고, 다른 하나는 분석 ID 단위 락과 결과 저장을 맡았다. 나머지 하나는 LLM이 호출한 툴의 실행 기록을 저장했다.

툴 기록은 최종 분석이 어떤 입력과 계산을 근거로 만들어졌는지 확인하는 자료다. 분석이 끝날 때 한 번만 쓰는 결과와 달리, 모델이 툴을 호출할 때마다 남는다. 그렇다고 모델이 다음 응답을 만드는 동안까지 DB 연결이 계속 필요한 것은 아니었다.

문제는 세션 단위 advisory lock이었다. 이 락은 락을 얻은 DB 세션과 수명을 같이하므로, 연결을 닫고 나중에 다시 연결하는 것만으로는 같은 보호가 이어지지 않는다. 잠금장치를 연결에 걸어 둔 상태에서 연결만 떼어낼 수는 없었다.

기존 구조를 유지하면 동시 분석 3건에 쓰기 연결 9개가 필요했다. 동시 수를 늘릴수록 DB에서 실제로 일하는 시간보다 외부 응답을 기다리며 연결을 잡고 있는 시간이 부담이 됐다. 연결 수 한도를 높이는 것만으로는 이 구조가 바뀌지 않는다.

또 다른 제약은 연결이 분석 전체의 수명을 따라간다는 점이었다. 모델 응답을 기다린 뒤 DB 연결이 끊어져 있으면, 이미 모델을 호출한 분석도 실패할 수 있었다. 이 문제는 운영 장애를 새로 재현했다는 뜻이 아니라, 기존 코드와 로컬 장애 시험으로 확인한 실패 경로다.

## 별도 만료 시간을 만들지 않고 기존 실행 슬롯을 재사용했다

대안 검토에서는 기존 구조 유지, DB 단계마다 연결하는 방식, 만료 시간이 있는 DB 실행권, 큐와 고정 워커 구성을 비교했다. 이 가운데 단계별 연결은 기존 클라우드 실행 구조를 유지하면서 대기 중 연결을 반환할 수 있었다. 다만 중복 실행을 막던 세션 락의 역할이 이미 다른 곳에 있는지부터 확인해야 했다.

클라우드에는 `analysis_execution_slots`라는 테이블이 있었다. 단건 분석을 실행하는 Step Functions의 실행 ARN을 기록하고, 같은 종류·ETF의 분석이 겹치지 않게 하며 전체 동시 실행 수를 제한하는 테이블이다. ARN은 여기서 어느 실행이 슬롯을 차지하고 있는지 구분하는 식별자다.

이 슬롯은 시간이 지났다는 이유만으로 회수하지 않는다. 실행 이력이나 ECS 조회에서 태스크가 `STOPPED`라는 증거를 얻거나, 해당 실행이 태스크 제출 단계에 도달하지 않았음을 확인해야 회수한다. ECS가 `MISSING`을 반환하거나 조회 결과가 비어 있다는 사실만으로는 종료했다고 판단하지 않는다.

만료 시간을 가진 별도 실행권을 추가하면 유효 기간과 갱신, 갱신하지 못한 실행을 처리하는 정책까지 관리해야 한다. 이번 변경에서는 기존 슬롯이 이미 맡고 있던 실행 제어를 재사용하기로 했다. 대신 **결과를 발행하는 순간에도 자신의 슬롯이 남아 있는지 확인**하는 조건을 붙였다.

모든 진입 경로를 한 번에 바꾼 것은 아니다. 실행 ARN을 받지 않는 구버전 클라우드 경로와 로컬 대시보드는 기존 락 방식을 유지했다. 따라서 “분석 엔진 전체에서 장기 연결을 없앴다”보다 “실행 ARN을 전달하는 클라우드 워커의 연결 수명을 줄였다”가 정확하다.

![기존의 장기 DB 연결 세 개와 DB 작업별 짧은 연결, 별도로 유지되는 실행 슬롯의 시간축](/assets/img/posts/edge-llm-db-connections/connection-lifetime.png)
_LLM을 기다리는 동안 DB 연결은 닫고, 실행 슬롯은 별도로 유지한다_

## 결과 발행 트랜잭션에서 슬롯이 남아 있는지 확인했다 {#publication-ownership}

분석 결과를 저장하는 [PublicationStore](https://github.com/alphaeveryday/edge/pull/1112)는 이미 완료된 분석이면 저장된 결과를 반환한다. 새로 발행해야 한다면 같은 트랜잭션 안에서 자신의 실행 ARN으로 슬롯 행을 조회한다. 핵심 SQL은 짧다.

```sql
SELECT 1
FROM analysis_execution_slots
WHERE execution_arn = %s
FOR SHARE;
```

행이 없으면 `OwnershipLost` 예외를 내고 새 결과를 발행하지 않는다. 행이 있으면 `FOR SHARE`로 잠근 상태에서 결과 저장을 이어간다. 단순히 “방금 조회했을 때 있었다”는 확인에서 끝나지 않도록, 확인과 저장을 같은 트랜잭션에 넣은 것이다.

슬롯 회수는 해당 행을 `DELETE`한다. 이 삭제와 발행의 `FOR SHARE`가 같은 행의 잠금을 두고 경합하므로, 권한 확인과 결과 저장 사이에 회수가 끼어들지 못한다. 먼저 잠금을 잡은 트랜잭션에 따라 두 경우로 나뉜다.

![발행이 먼저 슬롯을 잠그면 회수가 커밋까지 기다리고, 회수가 먼저 끝나면 슬롯을 찾지 못한 이전 실행의 새 발행이 거절되는 두 경우](/assets/img/posts/edge-llm-db-connections/publication-slot-race.png)
_슬롯 확인과 결과 저장을 같은 트랜잭션에 넣어 발행과 회수의 순서를 정한다_

이미 커밋한 분석 결과의 전달 등록에는 슬롯을 다시 요구하지 않는다. 그 단계는 새 분석을 발행하는 것이 아니라, 확정된 결과를 후속 전달 원장에 등록하는 일이다. 여기까지 같은 권한 검사를 적용하면 발행은 끝났지만 전달 등록 전에 중단된 실행의 복구를 막을 수 있다.

### 연결 재시도 — 모델을 다시 호출하지 않고 DB 단계만 반복한다

짧은 연결에서는 연결 생성 자체가 더 자주 일어난다. 일시적인 연결 거절이나 세션 종료는 해당 DB 단계 전체를 제한된 시간 안에서 재시도하도록 바꿨다. 제약 위반이나 입력 오류, SQL 문장 시간 초과까지 같은 방식으로 재시도하지는 않는다.

단계를 반복하려면 같은 요청을 다시 수행해도 결과가 달라지지 않아야 한다. 시작 기록은 같은 ID의 입력을 비교하고, 완료된 발행은 기존 결과를 반환한다. 툴 기록도 같은 ID가 있다는 이유만으로 성공으로 넘기지 않고, 저장된 내용까지 같을 때만 재사용한다.

이 조건 덕분에 DB 커밋은 끝났지만 응답을 받지 못한 경우에도 저장 상태를 다시 확인할 수 있다. 재시도 과정에서 LLM을 다시 호출하지 않으므로, DB 연결 문제 때문에 모델 작업 전체를 반복하는 범위를 줄였다. 다만 DB 장애가 재시도 제한을 넘기면 해당 분석은 실패할 수 있다.

발행 권한 검사는 이전 워커의 프로세스를 중단하는 기능이 아니다. 권한을 잃은 워커도 LLM 호출이나 자기 분석 ID에 묶인 툴 기록을 계속할 수 있다. 막는 것은 권한을 잃은 실행의 **새 결과 발행**이며, 모델 호출 비용까지 차단하거나 전체 처리를 정확히 한 번만 실행하도록 보장하지 않는다.

## 로컬에서는 연결을 점유한 시간의 합을 따로 측정했다 {#verification-results}

로컬 시험은 PostgreSQL 16과 실제 클라우드 워커·저장 코드를 사용했다. LLM은 실제로 호출하지 않고 30초 대기와 툴 호출 40회를 재현하는 테스트 코드로 대체했다. 원천 자료와 S3, Step Functions·ECS 응답도 시험용 대체 구현을 사용했다.

비교 지표는 **연결·초**다. DB 연결 하나를 10초 유지하면 10 연결·초이고, 세 개를 같은 10초 동안 유지하면 30 연결·초다. 실행 시간이 같아도 연결을 더 오래, 더 많이 유지하면 이 값이 커진다.

아래는 동시 37건, 역할별 연결 한도를 두지 않은 조건에서 기존 구조와 최종 구현을 비교한 결과다. 기존 구조의 3,392는 원시 측정 3,391.8을 반올림한 값이다. 당시 배포 동시 수를 그대로 재현한 운영 시험이 아니라, 연결 수명의 차이를 드러내기 위해 동시 수를 높인 로컬 시험이다.

| 측정 항목 | 기존 구조 | 최종 구현 |
|---|---:|---:|
| 쓰기 연결 점유 시간의 합 | 3,392 연결·초 | 20.6 연결·초 |
| 동시에 열린 쓰기 연결 최댓값 | 111개 | 21개 |
| 저장 완료 | 37/37건 | 37/37건 |

기존 구조에서는 37건이 각각 연결 세 개를 유지해 최대 111개가 열렸다. 변경 후에는 LLM 대기 시간이 연결 점유에 포함되지 않았다. 이 결과는 로컬에서 연결을 잡아 둔 시간을 줄였다는 근거이며, 실제 RDS의 연결 수 감소율이나 실제 모델 37건의 동시 처리 능력을 뜻하지 않는다.

쓰기 연결 20개·읽기 연결 6개로 역할 한도를 둔 별도 시험에서도 최종 구현은 37건을 모두 저장했다. 이때 쓰기 연결 점유는 11.1 연결·초였고, 읽기 연결 거절 이후 재시도는 67회였다. 한도를 둔 결과를 위의 무제한 조건과 섞어 더 좋은 전후 수치로 제시하지 않았다.

### 재시도 간격 — 동시에 다시 접속하면 연결 거절이 반복됐다

한도를 둔 초기 구현에서는 37건 중 36건만 저장됐다. 함께 연결을 거절당한 워커들이 같은 간격으로 다시 접속하면서, 한 실행이 재시도 제한을 소진했다. 재시도 대기 시간에 무작위 차이를 주는 지터를 넣은 뒤에는 반복 시험 세 번에서 모두 37건이 저장됐다.

성공 여부와 별도로 장애 위치도 확인했다. 모델 응답 뒤 5초간 DB 로그인을 거절하는 시험에서는 세 건이 모두 재시도로 완료됐고, 모델을 추가 호출하지 않았다. 발행 도중 세션을 강제로 끊는 경우와 커밋 응답을 잃는 경우에도 재시도 후 행 수가 기준과 일치했다.

통합 테스트는 발행과 슬롯 회수의 순서도 다뤘다. 발행 트랜잭션이 슬롯을 잠근 동안 회수가 기다리는 경우, 회수가 먼저 끝나 이전 워커의 발행이 거절되는 경우를 나눠 확인했다. 연결 수치가 좋아졌어도 이 보호가 깨졌다면 채택할 수 없는 변경이었다.

## 개발 환경의 병렬 실행에서는 분석 시작 대기가 줄었다

AWS 개발 환경에서는 실제 모델을 호출하는 [별도 시험](https://raw.githubusercontent.com/alphaeveryday/edge/91f92ee5aa33a1daa8d9b9222888c5e47b7b94ac/tests/loadtest/analysis-v2/README.md)을 진행했다. 2026년 10월 4일 정기 실행의 동시 수 3과, 같은 날 수동 실행의 동시 수 37을 비교했다. **두 실행 모두 DB 연결 방식을 바꾼 뒤**이므로 이 결과를 연결 변경 전후의 속도 비교로 읽으면 안 된다.

| 측정 항목 | 동시 수 3, 정기 실행 | 동시 수 37, 수동 실행 |
|---|---:|---:|
| 전체 배치 시간 | 76분 46초 | 13분 5초 |
| 첫 시도 시작까지 대기 중앙값 | 2,039초 | 17초 |
| 단건 분석 시간 중앙값 | 360초 | 354초 |
| 입력 / 저장 | 37종 / 34종 | 37종 / 34종 |
| 배치 최종 상태 | FAILED | FAILED |

전체 시간은 짧아졌지만 단건 분석의 중앙값은 거의 같았다. 가장 크게 줄어든 것은 분석 자체의 시간이 아니라 자기 차례를 기다리는 시간이었다. 동시 수가 낮을 때는 몇 분짜리 분석들이 앞선 분석이 끝나기를 기다렸고, 동시 수를 늘린 실행에서는 그 대기가 줄었다.

두 실행 모두 입력 오류가 있는 세 종을 저장하지 못했다. 유효 입력 34종의 저장과 전체 목표 37종의 저장은 다른 결과이므로, 배치 상태도 `FAILED`로 남았다. 팀원이 담당한 분석 로직과 입력 오류 원인 조사는 이번 연결 변경의 성과에 포함하지 않았다.

실험은 일요일 개발 환경의 단회 비교이며, 수동 실행은 12종으로 먼저 확인한 뒤 37종으로 확대했다. 실험 뒤에는 동시 수를 당시 값인 3으로 복원했다. 이후 [10월 6일 평시 설정이 12로 변경](https://github.com/alphaeveryday/edge/pull/1164)됐지만, 그 후속 설정이 이 표의 측정 조건을 바꾸지는 않는다.

개발 환경 로그에 남긴 연결 생성 시간과 DB 단계 시간도 연결·초와는 다르다. 연결 생성 시간은 성공한 연결을 만드는 비용이고, 단계 시간은 연결 준비와 처리 시간을 함께 포함한다. 다른 서비스가 사용하는 연결까지 섞인 RDS 전체 연결 수로 로컬의 감소율을 다시 계산하지 않았다.

## 마무리

LLM 대기 중 연결을 반환하는 일은 `close()` 위치를 옮기는 것으로 끝나지 않았다. 연결이 유지하던 락의 역할을 확인하고, 기존 실행 슬롯을 재사용하며, 새 결과를 저장하는 트랜잭션에서 그 권한을 검사해야 했다.

로컬 시험은 연결을 점유한 시간의 합과 장애 이후 저장 동작을 확인했다. 개발 환경 시험은 실제 모델을 실행하며 동시 수를 늘렸을 때 시작 대기가 어떻게 달라지는지 보여줬다. 지표와 환경을 분리해야 어느 변경이 무엇을 개선했는지 설명할 수 있다.

이 변경에서 남긴 기준은 DB 연결이 살아 있다는 사실과 결과를 발행해도 된다는 판단을 같은 것으로 취급하지 않는 것이다. 연결은 필요한 구간에서 사용하고, 발행 권한은 실행 기록과 트랜잭션으로 확인한다.
