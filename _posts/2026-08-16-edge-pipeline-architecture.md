EDGE는 장중 1분 작업과 정기 배치를 함께 처리하는 데이터 파이프라인이다. 장중에는 상주 worker가 데이터를 수집하고, 배치는 별도 task로 실행한다. 두 경로 모두 무엇을 계획했고 무엇이 실제로 끝났는지를 원장에 기록한다.

이 구조를 처음부터 그려놓고 시작한 게 아니다. 시작은 한 종목을 하루 한 번 분석하는 일 배치였고, 단계 네 개짜리 워크플로 하나면 충분했다.

처리 대상과 실행 주기가 달라질 때마다 작업의 경계와 상태를 관리하는 방식도 달라졌다. v1의 일 배치에서 v5의 Airflow 도입과 분석 엔진 v2 전환까지, 각 단계에서 무엇 때문에 구조를 바꿨는지 정리했다.

## 파이프라인의 발전 과정 {#architecture-evolution}

v1~v5는 파이프라인의 발전 단계다. 분석 엔진 v1·v2나 구조도 파일의 버전 번호와는 구분한다.

| 단계 | 팀이 요구한 것 | 변경이 필요했던 부분 | 재설계 기준 |
|---|---|---|---|
| v1 | 한 종목을 하루 한 번 | 없음 — 순서만 맞으면 됐다 | 단일 워크플로에 4단계 |
| v2 | 여러 ETF, 이어서 장중 1분 단위 설명 | 벤더 순차 호출, 수집 성공과 분석 완료가 한 실행 단위 | 최장 branch 병렬화 + 큐 경계 |
| v3 | 60초 window 안에서 처리 | 배치 원장에 분 단위 상태를 못 적음 | 상주 worker + 1분 원장 |
| v4 | 실시간·배치·운영의 공존 | 두 레인이 같은 소스를 동시에 소유 | 작업마다 단일 소유자 |
| v5 | 수집 배치 운영과 분석 엔진 v2 연결 | 배치 일정 관리, 가격 사건 접수와 장시간 분석, 정기 전망을 각각 관리해야 함 | Airflow 수집 배치 + SFN 단건 분석과 전망 배치 |

## v1. 하루 한 번의 분석 {#v1은-하루-한-번의-처리를-한-워크플로로-연결했다}

![EventBridge가 단일 Step Functions를 트리거하고 Ingest, Transform, Feature 생성, 분석 네 단계가 좌에서 우로 순서대로 이어지는 도면. 각 단계는 ECS Fargate task이고 아래쪽 저장 계층의 S3 raw/, S3 canonical/, S3 feature, EDGE Cloud RDS로 화살표가 내려간다](/assets/img/posts/edge-pipeline-architecture/pipeline-v1-daily-batch.png){: width="1701" height="715" }
_하루 한 번 한 종목이면 단계 넷을 한 줄로 거는 워크플로 하나가 부족할 데가 없다_

이때는 실행 순서를 지키는 것이 중요했다. EventBridge가 단일 Step Functions를 깨우면 Ingest → Transform → Feature → 분석이 차례로 돌았고, 각 단계는 ECS Fargate task 하나였다.

저장소는 `raw/`에 벤더 응답을 그대로 덧붙이고 `canonical/`은 같은 키가 다시 들어오면 멱등하게 병합하도록 갈랐다. 이 경계는 [S3와 RDB의 역할을 가르는 기준](/posts/rdb-vs-s3-data-pipeline/)에서 출발해 [raw·canonical·feature 계층](/posts/medallion-architecture/)으로 굳었다.

## v2. 수집과 분석의 분리 {#v2는-벤더별-수집과-후속-분석의-실행을-분리했다}

![뉴스 레인과 가격 레인이 위아래로 나란히 흐르는 도면. 각 레인의 수집·조회 ECS Fargate 뒤에 AWS SQS가 하나씩 놓여 있고, 그 뒤의 consumer가 DeepSeek API를 호출하거나 분석 결과 DB에 적재한다](/assets/img/posts/edge-pipeline-architecture/pipeline-v2-queue-boundary.png){: width="1701" height="767" }
_SQS 두 개가 들어간 자리가 수집 성공과 분석 완료를 서로 다른 실행 단위로 갈라놓은 경계다_

대상이 늘자 한 단계가 벤더를 순서대로 부르는 구조가 먼저 무너졌는데, 병렬 실행의 전체 시간은 갈래(branch)의 합이 아니라 **최댓값**에 좌우됐다. KRX 쪽만 병렬화하면 약 580초, KIS 쪽만 병렬화하면 약 579초로 사실상 제자리였다.

수집 성공과 분석 완료가 같은 실행 단위에 묶여 있으면 분석 한 건이 느려질 때 다음 분 수집이 통째로 밀린다. 그래서 벤더별로 task를 쪼개고, 그 사이에 SQS 두 개를 넣어 뉴스는 LLM 추출 consumer에게, 가격 변동 트리거는 분석 실행 consumer에게 넘겼다.

갈라놓고 나니 커밋하는 일과 발행하는 일이 같은 트랜잭션 안에 있지 않다는 문제가 남았고, 이 틈을 [outbox로 닫는 과정](https://jingi723.github.io/posts/edge-outbox/)이 다음 결정이었다.

## v3. 1분 주기와 상주 worker {#v3은-장전에-계획하고-상주-워커가-1분-작업을-처리했다}

![위쪽 장전 구획에서 EventBridge Scheduler가 08:40에 SFN을 깨워 Session Planner Task를 띄우고 desiredCount=1로 running/healthy를 확인한다. 아래쪽 장중 구획에서는 상주 Price Worker와 News Worker가 S3 raw/canonical에 저장하고 원장 DB에 job과 outbox를 남기며, Outbox Relay Task가 Price/News Job SQS와 DLQ로 발행해 가격 변동 판정 워커와 뉴스 추출 워커가 경쟁 소비한다](/assets/img/posts/edge-pipeline-architecture/pipeline-v3-minute-session.png){: width="2171" height="771" }
_매 분 새로 띄우는 대신 장전에 한 번 계획하고 상주 worker가 window를 받아간다 — 도면의 가격 소스 토스증권 표기는 2026-08-01 실측 당시의 사실이다_

1분마다 작업을 처리하려면 기동 시간도 고려해야 했다. 매 주기 컨테이너를 새로 띄우면 기동과 초기화에 쓰는 시간이 60초 window 안에서 그대로 차감된다.

그래서 계획과 실행을 시간축에서 갈랐다. 이 단계에서는 장전 08:40에 세션 플래너가 그날의 window를 한 번 계획하고, 장중에는 상주 Price·News Worker가 명시된 window를 받아서 처리했다. 세션 시작 시각과 worker 구성은 이후 달라졌지만, 계획과 실행을 분리한 방식은 유지했다.

worker가 상주하자 각 분의 작업을 누가 맡았고, 몇 번 재시도했으며, 발행까지 끝났는지 기록해야 했다. 일 배치 원장에는 그 상태를 적을 곳이 없어 session·window·job·outbox를 포함한 6테이블로 1분 원장을 새로 만들었다.

60초 안에 끝낼 수 있는지는 벤더의 호출 처리량에 달려 있었다. 1분 경로의 첫 벤더는 토스증권이었는데 로컬에서 348건을 replay하니 **70.631초**로 window를 10.631초 넘겼고, 초당 14.8건이 나오는 KIS로 기본 분봉 소스를 바꿨다. 토스가 느렸던 게 아니라 60초 window라는 내 요구가 그 시점의 유량 상한 위에 있었다.

## v4. 실행 경로와 작업 소유권 {#v4는-실행-경로마다-작업의-소유자를-정했다}

![세션 오케스트레이션, 장중 1분 레인, 세션 비결속 분석 레인, 배치 오케스트레이션과 배치(KST) 네 영역을 한 장에 그린 도면. 장중 1분 레인의 News·Price·업종지수·iNAV·공시 Worker와 배치 레인의 수집·정제·적재 워커가 각각 S3 raw/canonical과 DB로 흐르고, 오른쪽 위 주석에 DB 아이콘은 논리 저장소이며 물리 DB 분리를 의미하지 않는다고 적혀 있다](/assets/img/posts/edge-pipeline-architecture/pipeline-v4-four-lanes.png){: width="2181" height="2021" }
_네 레인이 같은 소스와 같은 S3, 같은 원장을 나눠 쥐고 있어서 남은 문제가 속도가 아니라 소유권이 된다_

실행 경로가 늘면서 문제가 된 것은 공시 수집처럼 같은 소스와 같은 CLI를 두 레인이 동시에 쥐는 상황이었다. 그러면 원장은 한쪽이 끝낸 일을 못 보고 영구 MISSED로 남기거나 양쪽이 각자 호출해 DART 한도를 중복으로 태우기 때문에, 작업마다 단일 소유자를 원장에 못박았다.

오케스트레이터가 성공으로 끝났다는 건 상태 머신이 끝까지 갔다는 뜻이지 데이터가 다 들어왔다는 뜻이 아니라, 계획을 먼저 적어두고 끝난 뒤에 실적과 대조하는 원장을 따로 뒀다. 2026년 8월 14일 거래일에 가격 분석 큐로 나간 job은 390건으로, 09:01부터 15:30까지의 장중 1분 window 수와 정확히 일치한다.

이 도면은 구현한 경로와 확장 목표를 함께 정리한 것이다. 네 영역이 전부 같은 완성도로 돌고 있다는 뜻은 아니다.

## v5. Airflow 도입과 분석 엔진 v2 {#current-architecture}

![2026년 10월 15일 EDGE 구성. 위쪽의 장중 상주 worker와 아래쪽의 배치 task가 S3 raw, canonical, PostgreSQL로 데이터를 처리한다. Outbox Relay는 Job SQS와 설명 SQS로 후속 작업을 전달하고, 배치 오케스트레이션은 Step Functions와 Airflow가 나누어 맡는다](/assets/img/posts/edge-pipeline-architecture/pipeline-current-2026-10-15.png){: width="3842" height="2162" }
_2026년 10월 15일 AWS 개발 환경의 구성이다. 반복해서 그린 S3·RDS·DeepSeek 아이콘은 별도 저장소나 서비스를 뜻하지 않는다. 오른쪽 분석 엔진의 내부 실행 구조인 접수 Consumer·Step Functions·Fargate는 이 개요도에서 생략했다. [원본 크기로 보기](/assets/img/posts/edge-pipeline-architecture/pipeline-current-2026-10-15.png)_


v4에서 작업마다 실행 주체를 정한 뒤에는 수집 배치를 운영할 기반과 새 분석 엔진을 연결하는 방식이 달라졌다. **수집 배치는 Airflow로 일부 옮겼고, 분석 엔진은 v2로 교체하면서 요청 접수와 실제 분석 실행을 분리했다.** 두 전환은 서로 다른 경로의 변경이다. 분석 엔진까지 Airflow에서 실행하는 구조는 아니다.

분석 엔진 v2의 분석 로직과 최초 클라우드 단건 실행·가격 큐 전환은 팀원이 담당했다. 나는 수집 파이프라인과 Airflow 이관, v2의 정기 전망 배치, 이후 DB 연결 수명과 실행 제어 보완을 맡았다. 엔진 내부의 분석 방법보다 파이프라인과 맞닿는 입력·실행·완료 기준을 중심으로 설명한다.

### 장중 수급부터 Airflow로

배치가 늘어나면서 일정·의존성과 실행 상태를 관리할 기반도 정리하려 했다. 기존 ECS 업무 코드와 원장은 유지하고, 배치 오케스트레이션을 Airflow로 옮긴 뒤 부족한 수집과 전망용 원천을 붙이는 순서를 선택했다.

첫 대상은 장중 수급이었다. 입력과 산출물이 명확해 기존 개발 환경의 결과와 대조할 수 있고, 외부 공급자는 KIS 하나로 제한하면서도 중복 실행과 재실행 문제를 검증할 수 있었다. **10월 3일 AWS 개발 환경에서 장중 수급을 Airflow 상시 운영으로 전환**했으며, 시장·뉴스·공시 등의 다른 수집 배치는 Step Functions를 유지했다.

Airflow는 ECS on EC2에서 구동한다. Airflow task가 중단돼도 외부 ECS 작업은 계속 실행될 수 있으므로, 재시도 때 실행 중인 작업에 재접속하고 종료 여부가 불명확하면 재실행을 보류했다. 이 선택과 전환 검증은 [Airflow 전환 글](/posts/airflow-ecs-reexecution/)에 정리했다.

### 가격 사건 접수와 분석 실행의 분리

기존 분석 엔진 v1의 SQS Consumer는 메시지를 받은 프로세스에서 분석을 수행했다. 처리가 성공해야 메시지를 삭제했고, 실패하면 SQS 재전달과 DLQ로 이어졌다. 분석이 길어지는 동안 Consumer도 그 요청을 처리하고 있었다.

v2의 Consumer는 원본 사건을 DB와 대조한 뒤 분석 요청을 접수하는 데 집중한다. **Step Functions 실행 접수와 요청의 DB 기록을 확인하면 SQS 메시지를 삭제한다.** 분석 완료를 기다리는 것이 아니다. 같은 사건이 재전달되면 기존 실행을 찾아 연결하므로, 접수 성공과 분석 완료를 서로 다른 상태로 봐야 한다.

| 구분 | v1 가격변동 경로 | v2 가격변동 경로 |
|---|---|---|
| Consumer의 역할 | 메시지를 받아 분석까지 수행 | 원본 사건 확인과 실행 접수 |
| 실제 분석 프로세스 | Consumer 프로세스 | 단건 SFN이 실행하는 별도 Fargate 태스크 |
| SQS 메시지 삭제 | 처리 성공 뒤 | SFN 접수와 요청 DB 기록 확인 뒤 |
| 접수 이후 상태 | Consumer 처리와 SQS 재전달 중심 | SFN 실행 상태와 DB 분석 결과를 별도로 확인 |

단건 SFN은 Fargate를 띄우기 전에 DB의 실행 슬롯을 확보한다. 가격변동 설명·전망·수동 API 요청이 이 제어를 함께 사용해 전체 동시 실행 수를 제한하고, 같은 분석 종류와 ETF의 작업이 동시에 실행되지 않게 한다. 자리가 없으면 SFN에서 기다리므로 **대기만 하는 분석용 Fargate 태스크를 띄울 필요가 없다.** 슬롯은 실행 ARN으로 식별하며, 종료가 확인되지 않은 작업의 자리를 시간이 지났다는 이유만으로 재사용하지 않는다.

10월 2일 전환 기록에는 AWS 개발 환경에서 실제 가격 사건이 SQS → SFN → DB 저장 → 데모 금융사 게시로 이어진 결과가 남아 있다. v1 Consumer를 멈추고 진행 중 작업을 확인한 뒤 같은 ECS 서비스를 v2 Consumer로 교체했다. 기존 설명 큐와 가격 판정 경로는 유지했다. ### 단건 실행을 재사용하는 정기 전망 배치

v2에는 가격변동 설명뿐 아니라 ETF 전망도 있었다. 처음 클라우드에 연결했을 때 전망은 사람이 한 건씩 시작해야 했으므로, 나는 기존 단건 실행을 재사용하는 배치 SFN을 추가했다. EventBridge Scheduler가 배치를 시작하고, 배치는 ETF별 단건 SFN을 호출해 저장 결과를 모은다. **전망 배치도 Airflow가 아닌 Step Functions에서 실행한다.**

예정된 분석 기준시각과 ETF, 시도 번호로 분석 ID를 정해 같은 작업을 다시 접수해도 완료된 결과를 재사용하게 했다. 실패한 항목만 새 시도로 처리하고, 실행 상태를 확인할 수 없으면 새 분석을 시작하지 않는다. 태스크가 종료됐다는 사실만으로 완료를 세지 않고, 해당 시도의 DB 발행 상태와 마감 시각을 확인한다. 일부 ETF가 미완료면 배치도 실패로 남는다. [전망 배치 도입 PR](https://github.com/alphaeveryday/edge/pull/1063)

처음에는 DB 연결 한도 때문에 순차 실행으로 시작했다. 공통 실행 제어가 연결된 뒤 병렬 실행을 시작했고, 이후 DB 연결 수명을 줄여 동시 실행 규모를 더 늘렸다. 모델 응답을 기다리는 동안 DB 연결을 반환하되, 결과 발행 트랜잭션에서 자기 실행 슬롯에 대한 권한을 다시 확인하도록 보완했다. 이 판단과 실험 조건은 [DB 연결 수명 글](/posts/edge-llm-db-connections/)에 따로 정리했다.

10월 15일 확인한 원격 설정은 매일 06:00 KST 시작, 08:00 마감이다. 이는 배치의 일정과 완료 판정 기준이며, 매 실행이 마감 전에 성공한다는 뜻은 아니다.

### 분석 기준 시각에 맞춘 원천 데이터

엔진 실행을 연결하는 것만으로 전망에 필요한 데이터가 준비되지는 않았다. 분석 기준시각까지 수집해 사용할 수 있었던 값을 조회할 수 있도록 원문과 판본을 보존하는 수집·정제·적재 경로를 추가하고, 원천 관측 DAG를 Airflow에서 정기 실행하게 했다.

초기 원천 관측 DAG의 일정은 09:10으로, 06:00 전망 뒤에 수집하는 순서였다. 재무 수집 대상도 전망 대상보다 좁았다. [후속 변경](https://github.com/alphaeveryday/edge/pull/1117)에서 두 경로가 같은 ETF 설정을 사용하도록 하고, 수집 일정을 05:20으로 앞당겼다. 일정과 대상을 맞춘 변경이며, Airflow 수집 성공을 기다렸다가 전망 SFN을 시작하는 의존성까지 연결한 것은 아니다.

그림 위쪽의 장중 상주 서비스와 아래쪽의 수집 배치는 이 원천을 공급한다. 장중 세션은 평일 07:45~16:10 KST이고, `Worker ×5`는 시세·뉴스·공시·iNAV·업종지수 다섯 종류를 묶은 표현이다. Job SQS 뒤에서는 뉴스 이벤트 추출과 가격 변동 판정을 하고, 설명 SQS의 가격 사건이 앞서 설명한 v2 실행 접수로 이어진다. 배치 이벤트 추출은 Step Functions 단계에서 수행한다.

### 실패한 적재를 다음 실행에서 이어받기

수집과 정제가 성공해도 적재가 실패하면 분석에 필요한 값은 DB에 없다. 정제가 통과시킨 파일을 실행별 **manifest**에 기록하고 적재가 그 범위만 읽도록 한 뒤에도, 실패한 입력을 다음 실행이 찾아야 하는 문제가 남았다.

뉴스 태깅은 끝났는데 적재가 롤백되면, 이미 태깅한 기사가 다음 실행의 변경 목록에서 빠져 자동으로 복구되지 않았다. [이 실패를 고친 변경](https://github.com/alphaeveryday/edge/pull/885)에서는 뉴스 분석 결과를 적재하는 `LoadAssertions`가 manifest별 소비 완료를 기록하고, 자기 소비 기록이 없는 범위를 다음 실행에서 다시 적재하게 했다.

공유 canonical 파일이 부분 실패 중에 바뀔 수 있는 문제도 있었다. ETF 구성종목·ETF 프로필·종목 프로필 세 마스터는 완전한 산출물을 불변 파일로 확정하고 **`latest-good` 포인터**가 그 파일을 가리키게 했다. 소비자는 세 포인터를 먼저 고정하고 검증한 뒤 DB에 반영한다.

실행 누락은 별도로 관리한다. 예정된 작업을 원장에 먼저 기록하고 Reconciler가 15분마다 실제 실행과 대조한다. 원장은 실행 여부를, 소비 기록은 뉴스 분석 결과의 재적재 여부를, 기준시점 조회는 분석에 쓸 원천을 판단하는 데 각각 사용한다.

## 마무리

가장 오래 남은 건 두 번의 오답이다. 병렬 실행의 전체 시간이 합이 아니라 최댓값이라는 것, 그리고 60초 안에 처리 가능한 범위가 벤더 호출 처리량에 달려 있다는 것. 두 번 다 "줄이면 되겠지"라는 직관이 산술과 실측 앞에서 틀렸다.

v5에서는 수집 배치의 오케스트레이션, 분석 요청의 접수, 실제 분석 실행을 구분하게 됐다. Airflow가 일부 수집 배치를 관리하고, Step Functions가 v2 분석의 대기와 실행을 관리한다. 그 사이에서 접수됐는지, 실행됐는지, 필요한 데이터와 결과가 저장됐는지를 따로 확인해야 파이프라인의 어느 부분이 끝났는지 알 수 있다.
