EDGE는 장중 1분 작업과 정기 배치를 함께 처리하는 데이터 파이프라인이다. 장중에는 상주 worker가 데이터를 수집하고, 배치는 별도 task로 실행한다. 두 경로 모두 무엇을 계획했고 무엇이 실제로 끝났는지를 원장에 기록한다.

이 구조를 처음부터 그려놓고 시작한 게 아니다. 시작은 한 종목을 하루 한 번 분석하는 일 배치였고, 단계 네 개짜리 워크플로 하나면 충분했다.

처리 대상과 실행 주기가 달라질 때마다 작업의 경계와 상태를 관리하는 방식도 달라졌다. 아래 네 단계는 초기 구조가 바뀐 과정이고, 그 뒤에 [2026년 10월 15일 기준 구성](#current-architecture)을 덧붙였다.

## 초기 구조의 변화 {#architecture-evolution}

v1~v4는 발전 과정을 설명하기 위해 나눈 단계이며, 뒤에 나오는 현재 구조도의 파일 버전과는 별개다.

| 단계 | 팀이 요구한 것 | 변경이 필요했던 부분 | 재설계 기준 |
|---|---|---|---|
| v1 | 한 종목을 하루 한 번 | 없음 — 순서만 맞으면 됐다 | 단일 워크플로에 4단계 |
| v2 | 여러 ETF, 이어서 장중 1분 단위 설명 | 벤더 순차 호출, 수집 성공과 분석 완료가 한 실행 단위 | 최장 branch 병렬화 + 큐 경계 |
| v3 | 60초 window 안에서 처리 | 배치 원장에 분 단위 상태를 못 적음 | 상주 worker + 1분 원장 |
| v4 | 실시간·배치·운영의 공존 | 두 레인이 같은 소스를 동시에 소유 | 작업마다 단일 소유자 |

## v1. 하루 한 번의 분석 {#v1은-하루-한-번의-처리를-한-워크플로로-연결했다}

![EventBridge가 단일 Step Functions를 트리거하고 Ingest, Transform, Feature 생성, 분석 네 단계가 좌에서 우로 순서대로 이어지는 도면. 각 단계는 ECS Fargate task이고 아래쪽 저장 계층의 S3 raw/, S3 canonical/, S3 feature, EDGE Cloud RDS로 화살표가 내려간다](/assets/img/posts/edge-pipeline-architecture/pipeline-v1-daily-batch.png){: width="1701" height="715" }
_하루 한 번 한 종목이면 단계 넷을 한 줄로 거는 워크플로 하나가 부족할 데가 없다_

이때는 실행 순서를 지키는 것이 중요했다. EventBridge가 단일 Step Functions를 깨우면 Ingest → Transform → Feature → 분석이 차례로 돌았고, 각 단계는 ECS Fargate task 하나였다.

저장소는 `raw/`에 벤더 응답을 그대로 덧붙이고 `canonical/`은 같은 키가 다시 들어오면 멱등하게 병합하도록 갈랐다. 이 경계는 [S3와 RDB의 역할을 가르는 기준](/posts/rdb-vs-s3-data-pipeline/)에서 출발해 [raw·canonical·feature 계층](/posts/medallion-architecture/)으로 굳었다.

## v2. 수집과 분석의 분리 {#v2는-벤더별-수집과-후속-분석의-실행을-분리했다}

![뉴스 레인과 가격 레인이 위아래로 나란히 흐르는 도면. 각 레인의 수집·조회 ECS Fargate 뒤에 AWS SQS가 하나씩 놓여 있고, 그 뒤의 consumer가 DeepSeek API를 호출하거나 분석 결과 DB에 적재한다](/assets/img/posts/edge-pipeline-architecture/pipeline-v2-queue-boundary.png){: width="1701" height="767" }
_SQS 두 개가 들어간 자리가 수집 성공과 분석 완료를 서로 다른 실행 단위로 갈라놓은 경계다_

대상이 늘자 한 단계가 벤더를 순서대로 부르는 구조가 먼저 무너졌는데, 병렬 실행의 전체 시간은 갈래(branch)의 합이 아니라 **최댓값**에 좌우됐다. KRX 쪽만 병렬화하면 약 580초, KIS 쪽만 병렬화하면 약 579초로 사실상 제자리였다.

수집 성공과 분석 완료가 같은 실행 단위에 묶여 있으면 분석 한 건이 느려질 때 다음 분 수집이 통째로 밀린다. 그래서 벤더별로 task를 쪼개고, 그 사이에 SQS 두 개를 넣어 뉴스는 LLM 추출 consumer에게, 가격 변동 트리거는 분석 실행 consumer에게 넘겼다.

갈라놓고 나니 커밋하는 일과 발행하는 일이 같은 트랜잭션 안에 있지 않다는 문제가 남았고, 이 틈을 [outbox로 닫는 과정](https://jingi723.github.io/posts/edge-outbox/)이 다음 결정이었다.

## v3. 1분 주기와 상주 worker {#v3은-장전에-계획하고-상주-워커가-1분-작업을-처리했다}

![위쪽 장전 구획에서 EventBridge Scheduler가 08:40에 SFN을 깨워 Session Planner Task를 띄우고 desiredCount=1로 running/healthy를 확인한다. 아래쪽 장중 구획에서는 상주 Price Worker와 News Worker가 S3 raw/canonical에 저장하고 원장 DB에 job과 outbox를 남기며, Outbox Relay Task가 Price/News Job SQS와 DLQ로 발행해 가격 변동 판정 워커와 뉴스 추출 워커가 경쟁 소비한다](/assets/img/posts/edge-pipeline-architecture/pipeline-v3-minute-session.png){: width="2171" height="771" }
_매 분 새로 띄우는 대신 장전에 한 번 계획하고 상주 worker가 window를 받아간다 — 도면의 가격 소스 토스증권 표기는 2026-08-01 실측 당시의 사실이다_

1분마다 작업을 처리하려면 기동 시간도 고려해야 했다. 매 주기 컨테이너를 새로 띄우면 기동과 초기화에 쓰는 시간이 60초 window 안에서 그대로 차감된다.

그래서 계획과 실행을 시간축에서 갈랐다. 이 단계에서는 장전 08:40에 세션 플래너가 그날의 window를 한 번 계획하고, 장중에는 상주 Price·News Worker가 명시된 window를 받아서 처리했다. 세션 시작 시각과 worker 구성은 이후 달라졌지만, 계획과 실행을 분리한 방식은 유지했다.

worker가 상주하자 각 분의 작업을 누가 맡았고, 몇 번 재시도했으며, 발행까지 끝났는지 기록해야 했다. 일 배치 원장에는 그 상태를 적을 곳이 없어 session·window·job·outbox를 포함한 6테이블로 1분 원장을 새로 만들었다.

60초 안에 끝낼 수 있는지는 벤더의 호출 처리량에 달려 있었다. 1분 경로의 첫 벤더는 토스증권이었는데 로컬에서 348건을 replay하니 **70.631초**로 window를 10.631초 넘겼고, 초당 14.8건이 나오는 KIS로 기본 분봉 소스를 바꿨다. 토스가 느렸던 게 아니라 60초 window라는 내 요구가 그 시점의 유량 상한 위에 있었다.

## v4. 실행 경로와 작업 소유권 {#v4는-실행-경로마다-작업의-소유자를-정했다}

![세션 오케스트레이션, 장중 1분 레인, 세션 비결속 분석 레인, 배치 오케스트레이션과 배치(KST) 네 영역을 한 장에 그린 도면. 장중 1분 레인의 News·Price·업종지수·iNAV·공시 Worker와 배치 레인의 수집·정제·적재 워커가 각각 S3 raw/canonical과 DB로 흐르고, 오른쪽 위 주석에 DB 아이콘은 논리 저장소이며 물리 DB 분리를 의미하지 않는다고 적혀 있다](/assets/img/posts/edge-pipeline-architecture/pipeline-v4-four-lanes.png){: width="2181" height="2021" }
_네 레인이 같은 소스와 같은 S3, 같은 원장을 나눠 쥐고 있어서 남은 문제가 속도가 아니라 소유권이 된다_

실행 경로가 늘면서 문제가 된 것은 공시 수집처럼 같은 소스와 같은 CLI를 두 레인이 동시에 쥐는 상황이었다. 그러면 원장은 한쪽이 끝낸 일을 못 보고 영구 MISSED로 남기거나 양쪽이 각자 호출해 DART 한도를 중복으로 태우기 때문에, 작업마다 단일 소유자를 원장에 못박았다.

오케스트레이터가 성공으로 끝났다는 건 상태 머신이 끝까지 갔다는 뜻이지 데이터가 다 들어왔다는 뜻이 아니라, 계획을 먼저 적어두고 끝난 뒤에 실적과 대조하는 원장을 따로 뒀다. 2026년 8월 14일 거래일에 가격 분석 큐로 나간 job은 390건으로, 09:01부터 15:30까지의 장중 1분 window 수와 정확히 일치한다.

이 도면은 구현한 경로와 확장 목표를 함께 정리한 것이다. 네 영역이 전부 같은 완성도로 돌고 있다는 뜻은 아니다.

## 현재 구성과 그동안의 변경 {#current-architecture}

![2026년 10월 15일 EDGE 구성. 위쪽의 장중 상주 worker와 아래쪽의 배치 task가 S3 raw, canonical, PostgreSQL로 데이터를 처리한다. Outbox Relay는 Job SQS와 설명 SQS로 후속 작업을 전달하고, 배치 오케스트레이션은 Step Functions와 Airflow가 나누어 맡는다](/assets/img/posts/edge-pipeline-architecture/pipeline-current-2026-10-15.png){: width="3842" height="2162" }
_2026년 10월 15일 AWS 개발 환경의 구성이다. 반복해서 그린 S3·RDS·DeepSeek 아이콘은 별도 저장소나 서비스를 뜻하지 않는다. [원본 크기로 보기](/assets/img/posts/edge-pipeline-architecture/pipeline-current-2026-10-15.png)_

그림 위쪽은 장중 상주 서비스, 아래쪽은 정기 배치다. 장중 세션은 한국 시각으로 평일 07:45에 시작해 16:10에 종료한다. `Worker ×5`는 시세·뉴스·공시·iNAV·업종지수 worker 다섯 종류를 묶어 표현한 것이며, 세션 시작과 각 데이터의 수집 시각은 구분한다.

이 시기에는 실행 경로를 나누는 것만으로 해결되지 않는 문제가 남았다. 정제는 끝났는데 적재가 실패하면 다음 실행이 무엇을 이어받을지, 분석 시점에 필요한 원천 데이터가 준비돼 있는지까지 관리해야 했다.

### 실패한 적재를 다음 실행에서 이어받기

raw는 원문 보존, canonical은 표준화와 품질 검사, PostgreSQL은 조회와 분석에 쓸 데이터 적재를 맡는다. 처음에는 후속 task가 저장소를 넓게 탐색해 입력을 찾았지만, 실행이 겹치거나 일부만 성공하면 이번 실행의 산출물을 구분하기 어려웠다. 그래서 정제가 통과시킨 파일을 실행별 **manifest에 기록하고, 적재는 그 범위만 읽도록** 바꿨다.

입력 범위를 정한 뒤에도 실패한 적재를 다시 처리하는 문제는 남았다. 실제로 뉴스 태깅은 끝났는데 적재가 롤백되자, 이미 태깅한 기사가 다음 실행의 변경 목록에서 빠져 자동으로 복구되지 않았다. [이 실패를 고친 변경](https://github.com/alphaeveryday/edge/pull/885)에서는 뉴스 분석 결과를 적재하는 `LoadAssertions`가 manifest별로 소비 완료를 기록하고, 다음 실행에서 자기 소비 기록이 없는 범위를 찾아 다시 적재하게 했다. 생산자가 처리했다는 사실과 소비자가 DB에 저장했다는 사실을 나눠야 했다.

마스터 데이터에는 다른 문제가 있었다. 공유 canonical 파일은 정제가 일부 실패해도 내용이 바뀔 수 있어, 성공한 실행을 골랐다고 해서 그때의 데이터를 읽는다는 보장이 없었다. ETF 구성종목·ETF 프로필·종목 프로필 세 마스터는 완전한 산출물을 별도 불변 파일로 확정하고, **`latest-good` 포인터**가 그 파일을 가리키도록 바꿨다. 소비자는 세 포인터를 먼저 고정하고 검증한 뒤 DB에 반영한다.

### 장중 수급부터 Airflow로

배치가 늘어나는 과정에서는 일정·의존성과 실행 상태를 관리할 기반도 정리하려 했다. 기존 ECS 업무 코드와 원장은 유지하면서, 배치 실행 관리를 Airflow로 옮긴 뒤 부족한 수집과 전망 경로를 붙이는 순서를 선택했다.

첫 대상은 장중 수급이었다. 입력과 산출물이 명확하고 기존 개발 환경의 결과와 대조할 수 있으며, 외부 공급자는 KIS 하나로 제한하면서도 중복 실행과 재실행 문제를 검증할 수 있었다. **10월 3일 AWS 개발 환경에서 장중 수급을 Airflow 상시 운영으로 전환**했고, 시장·뉴스·공시 등의 다른 배치는 Step Functions를 유지했다. Airflow는 ECS on EC2에서 구동한다. 실행 중인 작업에 재접속하고 결과가 불명확하면 재실행을 보류하는 판단은 [Airflow 전환 글](/posts/airflow-ecs-reexecution/)에 정리했다.

### 분석 기준 시각에 맞춘 원천 데이터

분석 엔진 v2가 테스트 데이터를 넘어 실제 원천을 사용하려면, 단순히 최신 값을 저장하는 것으로는 부족했다. 전망의 기준 시각까지 수집해 사용할 수 있었던 값을 조회할 수 있어야 했다. 이를 위해 원문과 판본을 보존하는 수집·정제·적재 경로를 추가하고, 원천 관측 DAG를 Airflow에 새로 만들어 정기 실행을 활성화했다.

대상과 일정도 전망에 맞춰야 했다. 초기 원천 관측 DAG의 일정은 오전 09:10으로, 06:00 전망 뒤에 수집하는 순서였다. 재무 수집 대상도 전망 대상보다 좁았다. [후속 변경](https://github.com/alphaeveryday/edge/pull/1117)에서 재무 수집이 전망과 같은 ETF 설정을 사용하도록 하고, 수집 일정을 05:20으로 앞당겼다. 이는 필요한 데이터가 전망 전에 준비되도록 한 설정이며, 모든 원천이 매번 빠짐없이 수집된다는 뜻은 아니다.

그림에서 분석 엔진으로 향하는 두 경로도 역할이 다르다. 장중에는 outbox를 Relay가 전달하고, Job SQS 뒤에서 뉴스 이벤트 추출과 가격 변동 판정을 수행한다. 분석 엔진 v2는 설명 SQS에서 가격 변동 사건을 받아 실행하고, 필요한 원천 데이터는 기준 시점에 맞춘 읽기 전용 조회로 가져온다. 배치 이벤트 추출은 Step Functions 단계에서 실행한다.

이렇게 경로가 늘어난 뒤에도 예정된 작업은 실행 전에 원장에 기록한다. Reconciler가 15분마다 실제 실행 기록과 대조해 빠진 슬롯을 찾는다. 실행 여부는 원장으로 확인하고, 뉴스 분석 결과의 재처리 여부는 소비 기록으로 판단한다. 분석에 사용할 값은 기준 시점 조회로 고른다.

## 마무리

가장 오래 남은 건 두 번의 오답이다. 병렬 실행의 전체 시간이 합이 아니라 최댓값이라는 것, 그리고 60초 안에 처리 가능한 범위가 벤더 호출 처리량에 달려 있다는 것. 두 번 다 "줄이면 되겠지"라는 직관이 산술과 실측 앞에서 틀렸다.

그 뒤의 변경은 앞 단계가 성공했다고 다음 단계에 필요한 데이터까지 준비된 것은 아니라는 문제에서 이어졌다. 적재 실패 뒤에는 남은 입력을 다시 찾을 수 있어야 했고, 전망 실행 전에는 대상과 시각에 맞는 원천이 필요했다. 현재 구조는 이런 실패와 요구를 처리하면서 실행 주체, 소비 완료, 조회 기준 시각을 각각 관리하도록 바뀐 결과다.
