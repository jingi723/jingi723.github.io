[선착순 쿠폰 발급 프로젝트](https://github.com/jingi723/coupon-system)에서 요청이 순간적으로 몰리자 DB 연결을 기다리는 요청이 쌓였다. 발급 수량의 정합성을 지키더라도, 사용자가 응답을 기다리는 시간까지 짧아지는 것은 아니었다. 폭주가 끝난 뒤 들어온 요청도 앞선 작업이 빠져나가기를 기다렸다.

Kafka를 붙인 첫 경로에서는 신청 접수와 실제 발급을 나눴다. API는 신청을 Kafka에 기록한 뒤 접수를 알리고, Consumer가 DB에서 발급 여부를 판단했다. 접수 이후 중단된 신청이 복구되는지, 최종 발급까지 얼마나 기다리는지를 각각 확인해야 했다.

이후에는 Redis에서 재고를 확보해 예약을 승인하고, Relay와 Kafka를 거쳐 DB 발급을 마치는 구조로 바꿨다. **예약 승인도 사용자에게 확정해 주는 결과**다. 승인한 예약이 장애 후에도 발급으로 이어지는지 확인한 다음, 최종 발급 대기를 줄이는 배치 Consumer 후보를 비교했다. 후보에서 확인한 수집·트랜잭션 규칙은 이후 앱의 선택 옵션으로 옮겨 다시 검증했다.

앞부분의 10월 2~3일 측정은 Redis 예약이 없던 Kafka 직접 접수 경로다. 이후의 [예약 경로와 복구](#reservation-recovery), [10월 14일 테스트 후보 비교](#batch-consumer-results), [10월 15일 실제 앱 검증](#app-batch-results)은 실행한 구성과 조건을 구분해 설명한다.

## 접수 성공과 쿠폰 발급 성공을 다른 응답으로 다뤘다 {#request-and-issue}

동기 경로의 HTTP 200은 발급 처리가 끝났다는 응답이었다. 당시 Kafka 직접 접수 경로의 HTTP 202는 해당 신청을 접수했다는 응답이었다. 아직 Consumer가 발급 가능 여부를 판단하지 않았으므로, 202를 받았더라도 최종 결과는 `ISSUED` 또는 `REJECTED`가 될 수 있다.

당시 API는 클라이언트가 보내는 `requestId`와 쿠폰·사용자 ID로 메시지를 만들었다. Producer의 전송 결과를 확인한 뒤 202와 `ACCEPTED`를 반환했다.

전송 도중 연결이 끊기거나 응답을 기다리다 시간 초과가 나면, 메시지가 기록되지 않았다고 확정할 수 없다. 브로커는 기록했지만 애플리케이션이 그 응답을 받지 못했을 가능성이 있기 때문이다. API는 이 경우 접수 여부를 확인하지 못했다는 오류와 함께 **같은 requestId로 재시도**하도록 안내했다.

새 ID를 만들면 Consumer에게는 새로운 신청으로 보인다. 같은 ID를 유지하면 이미 처리된 신청인지 DB 결과에서 확인할 수 있다. 한 ID로 다른 쿠폰이나 사용자를 보내는 요청은 충돌로 다뤄, 기존 결과를 엉뚱한 신청의 결과로 반환하지 않도록 했다.

Kafka에는 순간 유입을 기록해 두고 DB 처리 속도에 맞춰 꺼내도록 했다. 접수를 마친 뒤에도 발급 대기가 남으므로, 최종 처리량과 대기 시간은 별도로 측정해야 했다.

## 발급 수량과 이력, 요청 결과를 한 트랜잭션에 기록했다

당시 Consumer는 `CouponIssueProcessor.process()`를 호출했다. 이 서비스는 먼저 해당 요청 ID의 처리 결과가 있는지 확인하고, 결과가 있으면 쿠폰·사용자가 같은지 비교한 뒤 기존 결과를 반환한다. 재전달된 메시지를 처리할 때 수량을 다시 증가시키지 않는 첫 번째 조건이다.

처리 결과가 없으면 쿠폰의 유효성과 기존 발급 여부를 검사한다. 재고 반영은 현재 발급 수량이 총수량보다 작고 쿠폰이 활성 상태인 경우에만 증가하는 조건부 `UPDATE`를 사용했다. DB의 중복 발급 제약도 함께 유지했다.

발급 수량 변경, 발급 이력 저장, 요청 ID별 최종 결과 저장은 하나의 DB 트랜잭션에 넣었다. 수량만 늘었거나 이력만 남은 상태에서 결과가 누락되면, 같은 메시지를 다시 받았을 때 무엇을 재사용해야 하는지 판단하기 어려워진다. 세 기록이 함께 커밋되거나 함께 롤백돼야 한다.

실험 당시 처리 코드에서 기존 결과를 재사용하는 부분은 다음과 같다.

```java
var existing = resultRepository.findByRequestId(requestId);

if (existing.isPresent()) {
    CouponIssueResult result = existing.get();
    if (!result.getCouponId().equals(couponId)
            || !result.getUserId().equals(userId)) {
        throw new IllegalArgumentException(
                "같은 요청 ID에 다른 요청 신청 내용을 사용할 수 없습니다."
        );
    }
    return result;
}
```

이 검사는 `@Transactional`이 적용된 처리 메서드 안에 있다. 기존 결과가 없는 경로에서는 발급 처리와 결과 저장을 수행하며, DB 오류가 나면 트랜잭션 전체가 롤백된다. 거절도 요청에 대한 최종 결과이므로 `REJECTED`로 남긴다.

Kafka 설정은 자동 offset 커밋을 끄고, 레코드 단위 `RECORD`와 동기 커밋을 사용했다. Spring Kafka 컨테이너는 리스너 호출이 반환된 뒤 해당 레코드의 offset을 커밋한다. 이 구현에서는 별도 트랜잭션 서비스가 커밋을 마치고 반환한 다음 리스너가 반환하므로, DB 커밋이 offset 커밋보다 앞선다.

DB 커밋과 Kafka offset 커밋 사이에서 프로세스가 종료되면 같은 레코드가 다시 전달될 수 있다. Consumer는 DB에 저장된 요청 결과를 재사용해 **같은 발급을 반복하지 않도록** 했다.

## DB 커밋 뒤 JVM을 종료해 같은 레코드의 재전달을 확인했다 {#recovery-verification}

2026년 10월 2일 로컬 복구 시험은 실제 Kafka 3.7.0과 MySQL 8.0 Testcontainers, 별도 애플리케이션 JVM을 사용했다. 기존 개발용 서비스와 분리된 환경에서, DB에는 커밋됐지만 Kafka offset은 그대로인 지점을 확인한 뒤 앱 프로세스를 강제로 종료했다.

테스트 전용 프록시는 DB 트랜잭션 서비스가 반환한 뒤, Consumer가 Kafka 컨테이너에 반환하기 전에 리스너 스레드를 멈춰 세웠다. 활성 트랜잭션이 없다는 표식과 함께, 별도 JDBC 연결에서 발급 수량·이력·처리 결과가 각각 한 건씩 조회되는지 확인해 커밋 완료를 대조했다.

그때 처리한 레코드의 offset은 3이었다. Consumer 그룹의 커밋된 다음 읽기 위치는 여전히 3이고 토픽 끝 위치는 4였다. offset 3의 메시지는 존재하지만, 다음에는 4부터 읽으면 된다는 처리가 아직 기록되지 않은 상태다.

이 지점에서 앱 JVM을 `Process.destroyForcibly()`로 강제 종료하고, 같은 Consumer 그룹으로 새 JVM을 시작했다. API 재접수나 Producer 재발행 없이 기존 레코드가 다시 전달되는지 확인했다.

재시작 후에는 최초 전달과 동일한 topic·partition·offset·requestId가 관측됐다. DB의 수량·발급 이력·처리 결과는 각각 1을 유지했고, 발급 이력 ID와 처리 결과 ID도 바뀌지 않았다. 토픽 끝 위치는 4인 채 커밋 위치만 3에서 4로 이동했다.

같은 레코드가 재전달됐을 때 DB의 기존 요청 결과를 재사용했고, 추가 발급은 발생하지 않았다.

## Consumer가 멈춘 요청은 보관됐고 DB 오류 뒤에는 수동으로 재개했다

Consumer만 멈추고 API는 유지한 시험에서는 재고 2개인 쿠폰에 신청 3건을 보냈다. 세 요청은 모두 202를 받았지만, Consumer가 멈춘 동안 DB의 발급 수량·이력·결과는 모두 0이었다. Kafka lag는 3으로 남아 처리할 신청을 보여줬다.

Consumer를 재개한 뒤에는 두 건이 `ISSUED`, 재고가 부족한 한 건이 `REJECTED`가 됐다. 모든 요청 ID에 최종 결과가 남았고 lag도 0이 됐다.

DB 오류 시험에서는 특정 요청의 결과 저장을 거절하는 `CHECK` 제약을 테스트 DB에 추가했다. 수량 변경과 이력 저장을 거친 뒤 결과 저장이 실제로 실패하도록 만든 것이다. 처리 이후 세 기록이 모두 0임을 확인해 트랜잭션 롤백 범위를 검사했다.

이 오류는 `CommonContainerStoppingErrorHandler`를 통해 리스너를 중단시켰다. API는 살아 있어 후속 신청도 Kafka에 접수됐지만, 제약을 제거한 것만으로 Consumer가 다시 처리하지는 않았다. **오류 원인을 제거한 뒤 Consumer를 수동으로 재개**했다.

수동 재개 후에는 실패했던 offset 4가 다시 전달돼 처리되고, 이어 offset 5의 후속 신청이 처리됐다.

| 중단 조건 | 중단 시 확인한 상태 | 재개 뒤 확인한 결과 |
|---|---|---|
| Consumer 정지 | 접수 3건, DB 결과 0건, lag 3 | 발급 2건·거절 1건, lag 0 |
| DB 커밋 후 JVM 종료 | DB 결과 1건, offset 미커밋 | 같은 레코드 재전달, 추가 발급 없음 |
| 결과 저장 중 DB 오류 | 수량·이력·결과 전체 롤백 | 원인 제거·수동 재개 뒤 두 요청 처리 |

세 복구 시험은 Kafka의 메시지 보관 기간 안에서 수행했다. 여러 파티션·Consumer 사이의 경합, 브로커 디스크 손실, 복제본 장애와 장시간 장애는 검증 범위에 포함하지 않았다.

## 접수는 빨라졌지만 최종 결과를 확인하는 시간은 늘었다 {#latency-results}

10월 3일 로컬 폭주 비교에서는 접수 지연과 최종 결과 지연을 따로 측정했다. 접수 지연은 HTTP 호출 직전부터 202를 받기까지이고, 최종 결과 지연은 같은 전송 시각부터 별도 JDBC 조회에서 커밋된 결과를 처음 읽기까지다. 엔티티의 `processed_at`을 DB 커밋 순간으로 사용하지 않았다.

3초 폭주 시험의 목표 부하는 초당 100건으로 20초, 초당 1,200건으로 3초, 다시 초당 100건으로 30초였다. 실제 전송 시각에는 부하 발생기의 편차가 있어 아래 차트와 표는 공통 시작점의 예정 경계로 요청을 나눴다. Kafka 경로의 실제 전송·접수는 8,617건이었다. 클라이언트 시간 제한은 60초이고 재시도는 하지 않았다.

로컬 MySQL과 Kafka는 각각 CPU 1개·메모리 1GiB, DB 연결 풀은 10개였다. Kafka는 파티션 하나와 Consumer 하나로 순차 처리했다. 같은 호스트의 다른 작업과 캐시 상태까지 통제한 실험은 아니었다.

DB 조회는 약 250ms 간격으로 수행했다. 최종 결과 지연에는 실제 커밋 이후 다음 조회까지 기다리는 시간이 포함되므로, 평상시의 약 254ms를 쿠폰 한 건의 순수 DB 처리시간으로 해석할 수 없다.

차트의 값은 각 전송 구간에 속한 요청들의 집계다. 한 요청의 처리 순서를 그린 것이 아니며, 두 p95의 차이를 큐 대기 시간의 p95로 계산할 수 없다.

기존 동기 경로에서 폭주 구간의 발급 완료 p95는 2,435.10ms였다. 다만 아래 비교에서는 발급을 판단하고 저장하는 작업 구조도 함께 달랐다.

빠른 접수 응답 뒤에도 발급을 기다리는 요청은 남아 있었다. 대기하던 장소가 HTTP 처리 스레드와 DB 연결 풀에서 Kafka의 미처리 메시지로 옮겨간 것이다. 관측 최대 lag는 3,214였고, 시험 종료 시점에는 접수 8,617건의 요청·사용자·발급 이력 매핑이 모두 일치했다.

모든 발급은 완료됐지만, 최종 결과 지연이 사전에 정한 회복 기준을 연속된 두 개의 5초 구간에서 충족하는지는 확인하지 못했다.

이 비교는 Kafka 유무만 바꾼 실험도 아니다. 기존 동기 경로는 Redis에서 판정한 뒤 DB에 저장했고, Kafka 경로는 Redis 선차감 없이 DB에서 판정하며 요청별 결과까지 추가로 저장했다. 처리 동시성과 저장 작업이 함께 달라져, 지연 차이 전체를 Kafka 자체의 비용으로 단정하지 않았다.

시간 비교에는 유효한 세 번째 실행만 사용했다. 앞선 실행 중 하나는 관측 도구 문제로 부하 전에 중단됐고, 다른 실행은 호스트 시계가 뒤로 이동해 지연 비교에서 제외됐다.

### 10초 폭주 — 타임아웃된 신청도 DB에서는 발급돼 있었다

별도 과부하 비교에서는 폭주를 10초로 늘리고 클라이언트 시간 제한을 5초로 맞췄다. 동기 경로의 전송 17,002건 중 8,642건이 타임아웃됐지만, 최종 DB에서는 17,002건 모두 발급돼 있었다. 사용자에게는 결과를 알 수 없는 요청이었지만 서버에서는 발급이 계속 진행됐다.

Kafka 경로는 17,003건을 모두 202로 접수하고 최종 발급까지 마쳤다. 다만 마지막 요청 전송 뒤에도 약 16.7초 동안 추가 처리가 필요했다. 접수 응답 이후 초과 유입을 보관하고 순차 처리하는 시간이 필요했다.

과부하 비교에서는 두 경로 모두 최종 발급을 마쳤고, 접수 응답과 처리 대기의 차이가 드러났다. 중단 후 재전달과 중복 방지는 앞선 강제 종료 시험에서 확인했다.

## Consumer 시간의 대부분은 DB 처리 경로에서 쓰였다 {#consumer-cost}

같은 10월 3일의 Kafka 직접 접수 경로에서 Consumer 수와 offset 커밋 설정을 유지한 채, 적체를 처리하는 동안 DB 서비스 호출, offset 커밋, `poll()`에 쓰인 시간을 나눠 측정했다. 계측을 끈 실행과 켠 실행을 OFF→ON→ON→OFF 순서로 반복한 기록을 비교했다.

이 시험은 초당 1,200건을 10초 동안 보내는 조건을 사용했다. DB 구간은 트랜잭션 프록시에 들어가기 직전부터 실제 커밋과 정리가 끝나 반환할 때까지 측정했다. 커밋 완료는 독립 JDBC 조회와 트랜잭션 상태로 대조했다.

내부 계측을 켠 두 실행에서 DB 처리 경로는 같은 적체 구간 시간의 **91.8%와 92.2%**를 차지했다. 실제 `commitSync()` 호출부터 반환까지 측정한 offset 커밋은 각각 7.70%, 7.34%였다. 이 구성에서는 먼저 확인할 비용이 레코드 조회보다 순차 DB 처리 쪽에 있었다.

약 92%는 연결 확보, JPA·JDBC 처리, SQL, 커밋과 정리를 포함한 애플리케이션의 DB 호출 시간 비중이다. DB 서버의 CPU 사용률은 이 값으로 알 수 없다. 한 요청의 평균 DB 구간은 3.668ms와 3.258ms였지만, 앞선 요청이 쌓이면 자신의 처리 차례까지는 수십 초를 기다릴 수 있었다.

커밋 콜백으로 측정한 구간은 전체 적체 시간의 약 37~38%였고 DB 구간 안에 포함된다. 이를 약 92%에 다시 더하지 않았다. 서버의 COMMIT 통계와 파일 I/O 대기도 관측됐지만, 콜백 시간을 순수 디스크 동기화 시간으로 해석할 근거는 부족했다.

계측을 켠 두 실행이 일관되게 느려지지는 않았으나, 네 번의 비교만으로 오버헤드의 정확한 크기를 판단하기는 어려웠다. 당시에는 같은 DB 작업을 트랜잭션당 한 건과 여러 건으로 처리하는 비교를 후속 후보로 남겼다. 실제 배치 비교에 앞서, Redis에서 예약을 확정하고 전달·발급·조회를 연결하는 작업부터 진행했다.

## Redis에서 예약을 확정하고 승인한 예약을 DB에 반영했다 {#reservation-flow}

현재 경로는 **Redis 예약 → Relay → Kafka → DB → 결과 조회**다. 앞선 `ACCEPTED`는 Consumer의 발급 판단을 기다리는 신청이었지만, `RESERVED`는 Redis에서 재고를 확보해 승인한 예약이다. DB 반영까지 끝나 사용 가능한 발급이 되면 조회 결과가 `ISSUED`로 바뀐다.

예약 Lua는 행사 기간·재고·사용자 중복을 확인하고 재고 차감, 사용자 등록, 요청 ID별 예약 저장과 `pending` 등록을 한 실행에서 처리한다. 같은 요청 ID와 같은 신청 내용으로 재시도하면 기존 예약을 반환한다. API는 이 예약을 확인한 뒤 응답하며, Kafka 전송이나 DB 완료를 기다리지는 않는다.

Relay는 전달 중인 요청을 보관하는 `processing`을 먼저 확인한다. 남은 요청이 없으면 `LMOVE`로 `pending`의 요청을 `processing`으로 옮기고, 예약 내용을 Kafka에 전송한다. **Kafka 전송 성공을 확인한 뒤에만 processing에서 제거**하므로, 전송 전후에 앱이 멈춰도 재시작한 Relay가 남은 요청을 다시 시도할 수 있다.

전송 결과를 모를 때는 예약을 취소하거나 재고를 돌려놓지 않는다. 이미 Kafka에 기록됐을 수도 있기 때문이다. 현재 Relay는 하나만 실행하며, 전달 오류가 나면 요청을 남긴 채 일시 중단하고 원인 해결 후 명시적으로 재개하거나 앱을 재시작한다.

Consumer는 메시지의 요청 ID·쿠폰·사용자·승인 시각을 Redis 예약과 대조한 뒤 `processReserved()`를 호출한다. 이 메서드는 이미 발급한 요청이면 기존 결과를 반환하고, 새 요청이면 수량·발급 이력·처리 결과를 한 DB 트랜잭션으로 저장한다. DB 상한과 고유 제약도 유지해 예약과 DB가 어긋나면 처리를 멈춘다.

행사 기간은 **처리 시각이 아니라 Redis의 예약 승인 시각**으로 검사한다. 행사 중 승인한 예약을 DB 적체 때문에 행사 종료 후 처리하더라도 발급할 수 있어야 하기 때문이다. 첫 버전은 행사 전에 수량·기간을 고정하며 진행 중 증량과 예약 취소는 지원하지 않는다.

결과 조회는 요청 ID의 DB 결과를 먼저 찾는다. 아직 DB 결과가 없고 Redis에 예약이 있으면 `RESERVED`를 반환하므로, 사용자는 예약 승인과 발급 완료를 구분해 확인할 수 있다.

## 예약을 남긴 상태에서 전달과 발급을 다시 이어 갔다 {#reservation-recovery}

10월 14일에는 실제 HTTP 요청부터 Redis·Relay·Kafka·MySQL을 거쳐 결과를 조회하는 경로를 격리 환경에서 검증했다. Redis는 AOF의 `appendfsync always`와 전용 볼륨을 사용했고, Relay·Consumer·Kafka 파티션은 각각 하나였다. 별도 앱 JVM을 종료한 뒤에도 같은 저장소와 Consumer 그룹을 유지했다.

먼저 Redis 정상 재시작과 강제 종료 후 같은 볼륨으로 새 컨테이너를 띄워 재고·사용자·예약·정책·대기열의 키 덤프를 대조했다. 전체 연결 시험의 승인 3건은 복구 후 모두 `ISSUED`가 됐다. Consumer가 멈춘 동안에는 `RESERVED`로 조회됐고, 완료 후 같은 ID로 다시 신청해도 메시지나 발급이 추가되지 않았다.

이 시험의 행사 초기화와 첫 `processing` 이동은 테스트 코드가 준비한 상태였다. 실제 전달 도중 중단되는 경우는 별도 장애시험에서 확인했다.

- **Kafka 전송 전 종료:** 실제 LMOVE 직후 앱 JVM을 종료했다. 재시작한 Relay가 processing의 요청을 전달해 승인 2건 모두 발급됐다.
- **Kafka 전송 성공 후 종료:** 전송 성공을 확인했지만 processing에서 제거하기 전에 JVM을 종료했다. 재시작 후 재전송으로 Kafka 레코드는 3건이 됐지만, 승인·발급은 2건이고 기존 발급 ID도 유지됐다.
- **DB INSERT 실패:** 수량·이력·결과가 함께 롤백됐고 Redis 예약과 차감은 유지됐다. 오류 원인을 제거하고 Consumer를 수동으로 재개하자 실패 요청과 후속 요청이 모두 발급됐다.
- **DB 커밋 후 종료:** offset을 커밋하기 전에 JVM을 종료하고 같은 그룹으로 재시작했다. 동일 레코드가 재전달돼도 결과 ID·발급 ID·처리 시각과 수량이 유지됐다.

Relay의 재전송은 **새 offset의 메시지**를 만들 수 있고, Consumer의 재전달은 **같은 offset의 메시지**를 다시 받는 일이다. 두 경우 모두 요청 ID로 기존 DB 결과를 재사용했지만, 메시지 자체가 한 번만 전달된 것은 아니다. 각 장애시험에서는 승인한 요청 ID가 최종 결과와 발급 이력에 모두 대응하는지 확인했고, 마지막 `pending`·`processing`·lag도 0이었다.

Redis 시험은 프로세스 장애 뒤 같은 볼륨을 복원한 범위다. 디스크·볼륨 유실이나 다중 노드 장애까지 예약 무유실을 보장한 결과는 아니다. DB 실패도 특정 INSERT의 CHECK 제약 오류를 주입한 시험이며, 오류 원인 제거와 Consumer 재개는 수동이었다.

<details markdown="1">
<summary>복구 시험을 재현할 때 구분할 준비 과정</summary>

최초 Redis 재시작 시험은 테스트가 이전 공개 포트로 즉시 재접속해 실패했다. Docker의 포트를 다시 조회하고 준비 완료를 기다리도록 고친 뒤 두 시험이 통과했으며, 최초 실패 자료도 보존했다.

전달·DB 장애시험은 처음에 4개와 기존 전체 연결 2개가 통과했다. 이후 DB CHECK를 해당 요청 ID에만 걸도록 좁혀 시험 순서 의존성을 없애고 장애시험 4개를 다시 통과했다. 행사 준비는 테스트 fixture가 수행했고, 장애 이후에는 Consumer offset을 임의로 옮기지 않았다. 기존 전체 회귀 테스트를 한꺼번에 재실행한 결과는 아니다.

</details>

## Relay 전달을 개선한 뒤에도 최종 발급 대기는 남았다 {#reservation-performance}

복구가 확인된 전체 경로에 부하를 보내자 Redis `pending`과 Kafka 모두에 적체가 생겼다. 예약 응답을 빠르게 반환하는 것과 승인한 예약을 DB에 반영하는 속도는 별개의 문제였다. 먼저 Relay가 어느 호출에서 시간을 쓰는지 나누고, 이어 Consumer의 비용을 확인했다.

Relay 준비 단계는 `processing` 조회, 필요할 때의 `pending` 이동, 예약 내용 조회로 나뉘어 있었다. 테스트용 Lua 후보에서는 이 준비를 한 호출로 묶고, Kafka 전송 성공 확인과 `processing` 제거는 그대로 뒀다. 잘못된 필드나 자료형은 이동 전에 검사하며, 준비 후 전송 전 중단과 전송 성공 후 중단에서도 기존 복구 동작을 확인했다.

비교는 AOF always와 단일 Relay·Consumer·파티션, 계측 조건을 유지한 채 기존 → Lua → Lua → 기존 순서로 실행했다.

준비 비용과 폭주 중 전달률은 두 번 모두 개선됐지만, 최종 발급 지연은 일관되게 줄지 않았다. Redis의 최대 적체는 줄고 Kafka의 최대 lag는 늘었다. 전달이 빨라진 것만으로 전체 처리가 빨라졌다고 결론 내릴 수 없어, Lua 후보를 고정한 상태에서 현재 Consumer를 다시 계측했다.

### Consumer 계측 — 현재 경로에서도 DB 호출이 가장 큰 비중이었다

Consumer 계측을 OFF → ON → ON → OFF로 바꾸고, Redis 승인 조회·검증, DB 트랜잭션을 포함한 호출, offset 커밋을 나눴다. ON 두 실행에서 **DB 구간은 직렬 레코드 처리시간의 84.26%와 84.09%**였다. 앞선 Kafka 직접 접수 경로의 약 92%와는 다른 실험이다.

이 DB 구간은 트랜잭션 프록시에 들어가기 직전부터 실제 커밋과 정리가 끝나 반환할 때까지다. 분모는 한 Consumer가 레코드를 처리하며 순서대로 수행한 구간의 합으로, 사용자 대기시간이나 DB CPU 사용률이 아니다. DB 내부 SQL·JPA flush·트랜잭션 시작과 정리·fsync의 기여까지 분리하지는 못했다.

계측을 켠 실행에서는 초당 발급 완료 건수가 줄어 계측 영향도 배제할 수 없었다. 그래도 두 실행에서 가장 큰 비용 구간이 반복됐으므로, 다음에는 DB 작업을 여러 건 묶는 후보를 비교했다. Relay Lua 통합은 이 후속 실험에 사용한 테스트 후보이며 기본 서비스에 적용한 변경은 아니다.

### DB 전용 비교 — 처리량과 한 건의 완료시간은 다르게 움직였다

먼저 HTTP·Redis·Kafka를 제외하고 미리 준비한 같은 승인 입력 17,000건을 DB에 재생했다. 기존 `processReserved()`를 외부 트랜잭션에 참여시켜 트랜잭션당 1건 → 10건 → 10건 → 1건 순서로 처리했다. 동시성은 하나이고 MySQL 내구성 설정과 계측 조건도 같았다.

10건씩 묶었을 때 두 실행 모두 처리량이 늘었고 실제 커밋은 17,000회에서 1,700회로 줄었다. 같은 영속성 컨텍스트에서 쿠폰 조회를 재사용하고 flush 횟수도 줄어, 순수 커밋 비용만의 효과로 구분할 수는 없었다.

반대로 각 호출 시작부터 커밋·정리 후 반환까지의 p95는 늘었다. 앞에 처리한 요청도 같은 배치의 뒤 요청이 끝나야 함께 커밋되기 때문이다. 처리량의 이득을 확인한 뒤에는 실제 경로에서 요청을 모으는 대기까지 포함해 비교할 필요가 있었다.

## 최대 10건을 모아 처리하되 수집 중에는 DB 트랜잭션을 열지 않았다 {#batch-consumer-policy}

배치 후보는 **최대 10건, 첫 레코드를 poll로 받은 시각부터 10ms**를 수집 기준으로 정했다. 10건이 모이면 바로 처리하고, 기한이 지나면 모인 만큼 처리한다. 트래픽이 적을 때 남은 요청이 다음 신청을 계속 기다리지 않도록 하기 위한 조건이다.

수집과 Redis 예약 검증을 끝낸 뒤 외부 DB 트랜잭션을 시작한다. 그 안에서 기존 `processReserved()`를 순서대로 호출하고 배치 전체를 커밋하거나 롤백한다. 트랜잭션의 커밋과 정리가 끝나 반환한 다음, 마지막 레코드의 offset + 1을 `commitSync()`한다.

검증이나 DB 처리에 실패하면 Consumer를 멈추고 해당 배치의 offset을 커밋하지 않는다. 같은 그룹으로 재시작했을 때 배치를 다시 받아 처리하며, DB 커밋 뒤 중단됐던 요청은 기존 결과를 재사용한다. 처리 단위를 키우는 만큼 실패 시 다시 처리할 범위도 한 건에서 배치 전체로 넓어진다.

이때 사용한 코드는 `src/test`의 **테스트용 수동 Kafka Consumer**다. 단건과 배치 모두 같은 구현을 사용하고 `max.poll.records=10`도 같게 뒀다. 당시 서비스에는 Spring `RECORD` 단건 Consumer만 있었으며, 비교 중에는 자동 시작을 꺼 두 Consumer가 경쟁하지 않도록 했다.

## 같은 테스트 Consumer에서 최종 발급 지연이 줄었다 {#batch-consumer-results}

10월 14일 비교는 Redis 예약부터 Relay·Kafka·DB까지 전체 경로를 연결하고 **단건 → 배치 → 배치 → 단건** 순서로 실행했다. 재고 100,000개에 고유 요청 ID·사용자를 사용했고, 부하는 초당 100건 20초 → 1,200건 10초 → 100건 30초였다. HTTP 시간 제한은 5초이고 자동 재시도는 하지 않았다.

로컬의 Redis 7은 AOF always, CPU 0.5개·메모리 256MiB였고, MySQL 8과 Kafka 3.7은 각각 CPU 1개·메모리 1GiB였다. DB 연결 풀은 10개, Relay·파티션·Consumer는 각각 하나였다. 네 실행 모두 Lua Relay 후보와 Relay·배치 계측을 켰고, 실행마다 새 앱 JVM과 쿠폰을 사용하되 같은 격리 인프라를 재사용했다.

아래 **최종 발급 관측 지연**은 요청의 실제 전송 시각부터 외부 JDBC 조회가 DB 발급 결과를 처음 확인한 시각까지다. 약 250ms 주기의 관측 지연이 포함되며, p95는 폭주 구간만이 아니라 저부하·폭주·회복 구간의 전체 요청을 집계했다.

| 실행 순서 | 최종 관측 p95 | 승인·발급 |
|---|---:|---:|
| 1. 단건 | 46.064초 | 17,003건 |
| 2. 배치 | 20.686초 | 17,001건 |
| 3. 배치 | 17.652초 | 17,003건 |
| 4. 단건 | 48.547초 | 17,003건 |

네 번의 부하에서 **총 68,010건이 예약 승인되고 발급됐으며, 중복과 미완료는 없었다.** 요청 ID 집합과 쿠폰·사용자·발급 이력·결과·재고·수량을 대조했고, 미전송과 타임아웃도 없었다. 목표 부하의 명목 합계와 실제 건수 차이는 부하 발생기의 구간 경계에서 추가된 요청까지 집계한 결과다.

같은 테스트 Consumer 안에서는 두 번 모두 배치의 최종 발급 지연이 짧았다. 다만 트랜잭션 크기와 함께 수집 대기, offset 커밋 단위, JPA 조회 재사용과 flush도 달라졌다. 기본 Spring Consumer 대비 개선 배율이나 순수 DB 커밋 비용만의 효과로 계산하지 않았다.

배치 실행에서도 Redis `pending`은 최대 9,358/8,618건까지 쌓였다. Kafka lag가 줄었다는 이유로 전체 적체가 사라진 것은 아니다. 이 결과는 계측을 켠 로컬 비교이며, 공유 호스트·디스크·캐시와 실행 순서의 영향은 남아 있다.

### 저부하 — 10ms는 수집 기준이며 전체 응답시간의 상한이 아니다 {#batch-low-load}

저부하는 실제 전송 시각 기준 첫 20초의 요청으로 나눴다. 배치의 수집 대기 p95는 **10.691/10.729ms**였다. 수집 루프 시작부터 수집 종료까지 잰 값이며, DB 트랜잭션은 그 뒤에 시작한다. 10ms deadline은 첫 레코드의 poll 수신 시각을 기준으로 하지만 OS와 Kafka 클라이언트의 스케줄링 때문에 실제 수집시간이 이를 넘을 수 있다.

수집 대기와 요청부터 DB 완료까지는 다른 지표다. 짧은 대기를 확인하기 위해 DB 트랜잭션이 커밋·정리 후 반환한 시각도 단조 시계로 기록하고 JVM의 기준 시각에 연결했다. 이 값은 DB 서버 자체의 커밋 시각이 아니라, 정리가 끝나 애플리케이션에 제어가 돌아온 시각이다.

요청 전송부터 이 반환까지의 저부하 p95는 단건 211.667/109.268ms, 배치 129.968/132.636ms였다. 단건 첫 실행의 편차가 커 저부하 전체 p95가 일관되게 개선되거나 악화됐다고 결론 내릴 수는 없었다. 배치가 요청을 모으는 대기를 추가한다는 점과, 전체 지연의 변화는 나눠 봐야 했다.

### 장애시험 — 배치 전체 롤백과 커밋 후 재전달을 확인했다 {#batch-recovery}

부하 비교 전에는 다음 세 장애·경계 시험을 통과했다.

- **남은 요청 처리:** 쌓인 13건을 10건 + 3건으로 처리하고, 이후 단독 1건도 다음 요청 없이 처리했다. 수집 중에는 DB 트랜잭션이 없었다.
- **배치 중 INSERT 실패:** 10건 중 다섯 번째 INSERT를 실패시키자 앞의 네 건을 포함한 수량·이력·결과가 모두 롤백되고 offset이 유지됐다. 재시작 후 실패한 10건과 후속 3건이 완료됐다.
- **배치 커밋 후 종료:** DB에 10건을 커밋한 뒤 offset 커밋 전에 JVM을 종료했다. 같은 offset·요청 ID의 배치가 재전달돼도 기존 결과 ID·발급 ID와 수량이 유지됐다.

최초 실행은 1개 통과, 2개 실패였다. 한 시험은 오류 주입용 CHECK가 다른 쿠폰의 기존 사용자에게도 걸렸고, 다른 시험은 강제 종료 뒤 Consumer 그룹이 재할당되기 전에 관찰 시간이 끝났다. CHECK를 해당 쿠폰으로 한정하고 관찰 한도를 90초로 늘린 뒤 세 시험이 통과했다. 서비스 로직이나 Kafka session timeout을 바꾼 결과는 아니다.

이 비교 당시에는 배치 후보를 서비스에 반영하지 않았다. 앱에 적용하려면 Consumer 선택 방식과 실패 후 재개·종료 절차까지 정해야 했다. 마지막 단건 부하에서는 전량 처리와 최종 스냅샷 이후 앱 종료 중 Relay가 이미 종료된 Redis 연결 자원에 접근하는 오류도 다시 남았다. 후속 앱 부하에서 오류 로그는 없었지만, 종료 순서 문제의 수정을 검증한 시험은 아니므로 별도 과제로 남겼다.

## 앱에서 선택하는 배치 Consumer {#app-batch-results}

10월 15일에는 최대 10건·10ms 규칙을 실제 앱의 `CouponBatchConsumer`에 반영했다. **기본값은 기존 단건 Consumer**이며, `COUPON_BATCH_ENABLED=true`로 실행할 때 배치 Consumer가 동작하고 단건 리스너의 자동 시작은 꺼진다. 두 Consumer가 같은 신청을 경쟁해서 처리하지 않도록 선택을 분리했다.

수집과 Redis 예약 검증을 마친 뒤 트랜잭션을 시작하고, 커밋·정리가 끝난 다음 offset을 커밋하는 순서는 후보와 같다. 단건 Consumer의 예약 검증과 `processReserved()`를 공유하며, 수집 중 파티션 소유권이 바뀌거나 처리에 실패하면 배치 작업자를 중지한다. 원인을 제거한 뒤 같은 그룹으로 앱을 수동 재시작해 이어서 처리한다.

작업자가 멈춰도 API는 예약을 계속 받을 수 있으므로, API 응답만으로 발급 경로의 정상 여부를 판단할 수 없다. offset 커밋 오류도 브로커 반영 여부를 확정할 수 없는 경우가 있어, 재시작 후 같은 요청이 전달되더라도 기존 DB 결과를 재사용해야 한다. 현재 옵션과 검증은 단일 파티션·Consumer를 대상으로 한다.

### 앱에서 다시 확인한 실패 처리

테스트 후보의 통과 결과만으로 앱의 복구를 대신하지 않았다. 별도 앱 JVM에서 13건이 10건과 3건으로 나뉘어 처리되고, 이후 단독 1건도 다음 신청 없이 처리되는지 확인했다.

다섯 번째 INSERT를 실패시킨 시험에서는 배치 전체가 롤백되고 offset이 유지됐다. DB에 배치를 커밋한 뒤 offset 커밋 전에 앱을 종료한 시험에서는, 같은 그룹으로 재시작해 재전달된 요청의 기존 결과 ID·발급 ID와 수량이 유지되는지 확인했다. 앱 배치 장애시험 3개와 예약 DB·기존 단건·배치 단위 시험을 합친 선택 테스트 34개가 통과했으며, 전체 프로젝트 회귀시험을 뜻하지는 않는다.

### 실제 앱의 전체 경로 비교

성능도 `CouponSystemApplication`을 실행해 다시 측정했다. 이번 단건 기준은 **기존 서비스의 Spring RECORD Consumer**이고, 배치는 앱에 추가한 수동 poll Consumer다. Relay는 기존 서비스 구현을 사용했으며, 10월 14일 후보 비교에 쓰인 Lua Relay와 내부 상세 계측은 사용하지 않았다.

로컬 격리 환경에서 Redis AOF always, 단일 Relay·파티션·Consumer, DB 풀 10개를 유지했다. 자원은 MySQL·Kafka 각각 CPU 1개·1GiB, Redis CPU 0.5개·256MiB였다. 재고 100,000개에 초당 100건 20초 → 1,200건 10초 → 100건 30초를 보내고, HTTP 시간 제한 5초와 재시도 없음도 동일하게 적용했다.

단건 → 배치 → 배치 → 단건 순서로 실행했지만, 첫 단건에서 wall clock과 단조 시계의 변화량에 약 1.995초 차이가 생겼다. 이 실행은 지연 비교에서 제외하고 새 격리 인프라에서 단건을 추가 측정했다. 따라서 **정합성은 전체 5회, 유효한 성능 비교는 4회**다.

아래 예약 응답 지연은 HTTP 요청 시작부터 예약 승인 응답까지다. 최종 발급 관측 지연은 요청 전송부터 외부 DB 조회에서 발급 결과를 처음 확인할 때까지이며, 목표 주기 250ms의 조회 지연을 포함한다. 두 지표 모두 각 실행의 전체 요청을 집계했다.

| 실행 | 예약 응답 p95 | 최종 관측 p95 |
|---|---:|---:|
| 단건 2 | 8ms | 63.819초 |
| 단건 재측정 | 7ms | 67.272초 |
| 배치 1 | 14ms | 48.067초 |
| 배치 2 | 10ms | 40.744초 |

전체 5회에서 **승인한 85,012건이 모두 발급됐고 중복과 미완료는 없었다.** 승인 ID와 Redis 예약, DB 결과·발급 이력, 사용자·쿠폰, 수량과 재고를 대조했다. 타임아웃과 미전송도 없었다.

유효한 두 배치 실행의 최종 관측 p95는 두 단건 실행보다 낮았다. 다만 예약 응답 p95는 배치 쪽이 더 높았고, 배치 실행의 Redis `pending`도 최대 11,208/10,952건까지 쌓였다. Kafka lag가 최대 78/867건으로 줄어도, Kafka에 도착하기 전 예약의 전달 대기는 남아 있었다.

이 결과는 앞선 후보의 46.1~48.5초 → 17.7~20.7초를 갱신하는 수치가 아니다. Relay와 계측 조건, 단건 Consumer 구현이 달라 각각의 실험 안에서 비교해야 한다. 이번에도 프레임워크·수집·트랜잭션·offset 단위가 함께 달라졌고, 재측정의 새 인프라와 공유 호스트·캐시 편차가 남아 있어 일반적인 개선 배율이나 순수 DB 커밋 비용의 효과로 확대하지 않았다.

앱 옵션 반영과 로컬 검증까지 마친 결과이며 상용 배포 성과는 아니다. 10ms 역시 첫 poll 수신 이후의 수집 기준으로, 요청부터 발급까지의 시간이나 엄격한 실제 시간 상한을 뜻하지 않는다. 앱 부하에서는 내부 건별 시간을 다시 계측하지 않았으므로, 외부 DB 관측만으로 저부하의 10ms 대기 비용을 정밀하게 판단하지는 않았다.

## 마무리

처음 Kafka를 붙였을 때는 신청을 받아 둔 `ACCEPTED`와 발급 결과를 나눴다. 현재는 Redis가 재고를 확보해 `RESERVED`를 응답하고, 승인한 예약을 DB에 반영해 `ISSUED`로 제공한다. 사용자에게 예약을 확정해 주는 일과 그 예약의 발급을 끝내는 일에 각각 책임이 있다.

Redis에는 재전송할 예약을 남기고, DB에는 수량·발급 이력·결과를 함께 커밋했다. Relay의 재전송과 Consumer의 재전달이 발생해도 기존 결과를 재사용하는지, DB 오류 뒤 예약을 유지한 채 다시 처리할 수 있는지 확인했다.

Relay 준비가 빨라져도 최종 발급 지연이 일관되게 줄지 않아 Consumer를 계측했고, DB 전용 비교와 전체 경로의 후보 실험을 거쳐 앱에 배치 옵션을 추가했다. 실제 앱에서도 최종 발급 대기는 줄었지만 예약 응답과 Redis 적체까지 개선된 것은 아니었다. 한 번의 성공 응답이나 Kafka lag만으로 판단하지 않고, 승인한 예약이 발급으로 이어지는지와 어느 구간에서 기다리는지를 함께 확인해야 했다.
